> 生效日期：2026-08-27

## 1. 三条工作流

| 工作流 | 解决的问题 | 本地技能 |
|---|---|---|
| PM / 需求 | 做什么、为什么做、怎样验收 | `fsm-pm-workflow` |
| 架构 | 高风险能力怎样实现才安全、兼容、可回滚 | `fsm-architecture-workflow` |
| 开发交付 | 怎样计划、测试、审查、留证并完成本地交付 | `fsm-development-workflow` |

三个工作流按需串联，不要求每个改动走完整链路。

`.agents/skills/fsm-*` 是工作流技能的仓库内规范版本，`.claude/skills/fsm-*` 是本地 Claude 镜像。修改工作流时必须同步两处并校验内容一致，避免不同代理执行不同规则。

## 3. 路由规则

### 3.1 快速通道

同时满足以下条件时，可以不建工作包：

- 最多一个文件、约十行净修改；
- 行为已经确认，不需要调查才能确定范围；
- 不涉及鉴权、支付、退款、库存、状态机、MQ、缓存并发、数据库迁移、公开 API 或跨服务契约。

快速通道仍要运行相关验证并报告真实结果。纯文档纠错可以走快速通道。

### 3.2 标准开发通道

阶段 B 已列明的普通修复直接引用 B 编号，不重复创建 PRD：

```text
阶段 B 条目或已确认 PRD
  → workpack plan
  → 用户确认
  → 测试先行与实现
  → 独立只读审查
  → evidence
  → 本地验证
  → 本地归档，或经用户授权进入 push → PR → CI → merge
```

一个工作包只包含一至三个紧密相关、可以独立验收的切片。

### 3.3 架构门

新增或实质改变下列内容时，先走 Design → 独立 Review → 用户确认：

- 支付或退款外部契约；
- 普通订单、退款、秒杀库存或状态机；
- Redis/MySQL 跨存储一致性；
- RabbitMQ 投递、重试、死信和对账；
- 数据库迁移或破坏性数据变更；
- 鉴权、资源归属、凭据边界；
- 公开 API 或 Java/Python/前端跨服务契约。

阶段 B 已经确认且没有新歧义的决定可以直接引用，不重复写 Design。预计 B5、B6、B10 在出现新设计选择时最可能触发架构门。

### 3.4 新业务 PM 通道

阶段 B 之外的新增用户能力走：

```text
方向提议 → 用户确认 → PRD → PRD Review → 用户确认 → 开发
```

PRD 状态为 `草稿 → 已确认 → 进行中 → 完成`，PRD frontmatter 与 `docs/prd/README.md` 必须同步。

## 4. 本地开发与审查

- 功能、Bug、重构和行为变化遵循仓库 `test-driven-development` 技能。
- 工作开始前先确认不会覆盖当前工作树中用户或其他代理的修改。
- 单人串行开发可以使用当前分支；并行或文件可能重叠时使用独立分支和 worktree。
- 独立审查使用只读上下文，结论写入 `review.md`；P0/P1 存在即 FAIL。
- 当前环境无法获得独立审查时记录 `tooling_blocked`，不能冒充 PASS。
- 标准 workpack 只有在 `review.md` PASS、AC 证据完整和新鲜验证同时满足后，才能标记本地完成；快速通道不建 workpack，以相关验证和真实结果报告为完成依据。
- 未经用户明确要求，不执行 commit、push、建 PR、合并或修改远程仓库设置。
- 经用户授权进入远程交付时，必须使用独立分支，CI 与敏感扫描全绿后才能合并；不得直推 `master` 或绕过失败检查。

## 5. 本地验证矩阵

| 改动范围 | 完成前验证 |
|---|---|
| Java 后端 | 开发期间运行聚焦测试，交付前在 `backend/` 执行 `mvn test` |
| 用户端 | 在 `frontend/fashion-client/` 执行 `npm run build` |
| 管理端 | 在 `frontend/fashion-admin/` 执行 `npm run build` |
| Python Agent | 在 `agent-service/` 执行 `python -m pytest -q` |
| 所有修改 | `git diff --check`、敏感信息检查、限定范围 diff 复核 |

当前两个前端没有 test/lint/typecheck 脚本，只能记录生产构建证据，不能声称前端单元测试或类型检查通过。Python 环境若缺少依赖，必须记录具体阻塞而不是标为通过。

## 6. Workpack 状态

```text
待确认 → 进行中 → 待审查 → 本地已验证 → CI 验证中 → 已归档
```

- `待确认`：计划已写，等待用户确认。
- `进行中`：用户已确认，正在测试和实现。
- `待审查`：实现和相关测试已完成，等待独立审查。
- `本地已验证`：Review PASS，AC 证据和本地验证完整。
- `CI 验证中`：功能分支已推送并建立 PR，等待全部远程检查通过。
- `已归档`：需求索引、进度表和工作包索引已经同步。

## 7. GitHub 交付边界

- 阶段 B 不重新拆写为十一份 PRD。
- 历史 Phase 不补 PRD、Issue 或 workpack。
- 已存在的 B1 未提交修改保持原样，不因迁移被重置或改写。
- GitHub Actions、Issue/PR 模板和 CODEOWNERS 规则见 [GitHub协作与CI.md](GitHub协作与CI.md)。
- 远程操作仍逐次受用户授权约束；工作流可用不等于允许自动 push、合并或修改设置。
- 基础 CI 只做测试、构建和敏感扫描，不包含 Docker 发布、数据库迁移或生产 CD。
- 远程 CI 结果必须来自 GitHub 对目标提交的真实检查，不能用本地等价命令冒充。
