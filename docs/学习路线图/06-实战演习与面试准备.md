## Step 6.1 全链路压测

### 压测方案设计

**目标：** 摸清系统在秒杀场景下的容量上限和各环节瓶颈

**JMeter 脚本要点：**

- 线程组：Step 递增（100、200、500、1000）
- 持续时间：每组持续 2 分钟
- 监听器：聚合报告（TPS、平均RT、TP90、TP99、错误率）

**压测计划：**

| 轮次  | 并发数  | 目的          |
| --- | ---- | ----------- |
| 1   | 100  | 基线测试        |
| 2   | 500  | Redis 连接池测试 |
| 3   | 1000 | 全链路瓶颈       |
| 4   | 2000 | 极限容量        |

**监控指标：**

| 指标       | 工具                    | 说明         |
| -------- | --------------------- | ---------- |
| TPS / RT | JMeter 聚合报告           | 系统吞吐量和响应时间 |
| CPU / 内存 | top / htop            | 系统资源       |
| GC 情况    | jstat -gcutil         | GC 频率和耗时   |
| Redis 连接 | redis-cli CLIENT LIST | 连接数        |
| MQ 堆积    | RabbitMQ 管理界面         | 队列长度       |
| DB 连接    | Druid 监控              | 活跃连接数      |
| 慢查询      | MySQL slow_query_log  | 慢 SQL      |

**瓶颈分析顺序：**

1. 先看应用层（CPU、内存、GC）
2. 再看中间件（Redis 连接、MQ 堆积）
3. 最后看 DB（连接数、慢查询）

## Step 6.2 故障模拟演习（10 场）

### 场景 1：Redis 宕机

- **模拟**：`redis-cli DEBUG SLEEP 30` 或直接停掉 Redis
- **现象**：Redis 操作超时，Lua 脚本失败，秒杀接口不可用
- **处理**：降级到本地 Caffeine 缓存、返回秒杀繁忙提示
- **验证**：Redis 恢复后自动重连，业务恢复正常

### 场景 2：RabbitMQ 宕机

- **模拟**：停掉 RabbitMQ 服务
- **现象**：秒杀消息发送失败，下单失败
- **处理**：catch 异常，消息落库，定时重试
- **验证**：MQ 重启后，补偿任务自动将落库消息重新发送

### 场景 3：MySQL 死锁

- **模拟**：高并发 UPDATE 同一行 + 不同事务顺序
- **现象**：`Deadlock found when trying to get lock`
- **处理**：`@Retryable` 自动重试
- **验证**：业务最终成功，死锁不导致订单丢失

### 场景 4：磁盘写满

- **模拟**：`dd if=/dev/zero of=/tmp/fill bs=1M count=...`（注意不要真的写满系统盘）
- **现象**：日志写不进去，应用可能异常
- **处理**：配置 logback 日志滚动策略（按大小、按天），保留最近 7 天
- **验证**：日志文件自动切割，最旧日志自动删除

### 场景 5：OOM

- **模拟**：调用 OOM 测试接口（Step 4.2 的堆溢出代码）
- **现象**：`OutOfMemoryError: Java heap space`
- **处理**：`-XX:+HeapDumpOnOutOfMemoryError` 自动抓堆，`-XX:+ExitOnOutOfMemoryError` 自动退出
- **验证**：生成 `heap.hprof` 可用 MAT 分析

### 场景 6：网络分区（模拟延迟）

- **模拟**：`tc qdisc add dev eth0 root netem delay 2000ms`（加 2s 延迟）
- **现象**：接口超时，RT 飙升，连接池被占满
- **处理**：配置超时时间（HTTP 5000ms，Redis 3000ms，DB 5000ms）
- **验证**：超时后快速失败，不阻塞连接池

### 场景 7：热点 key 打爆 Redis

- **模拟**：1000 并发请求同一个商品 key
- **现象**：Redis 单 key QPS 极高，Slave 可能跟不上
- **处理**：本地缓存兜底
- **验证**：本地缓存命中后，Redis QPS 下降

### 场景 8：DB 连接池满

- **模拟**：慢 SQL 导致连接不释放 + 高并发
- **现象**：`Cannot get connection from pool`
- **处理**：Druid 配置 `max-wait=5000`，超时报错而不是一直等；`remove-abandoned=true` 自动回收泄漏连接
- **验证**：监控活跃连接数变化

### 场景 9：消息积压

- **模拟**：消费者加 Thread.sleep(5000) 模拟处理慢
- **现象**：队列消息数暴涨
- **处理**：移除 sleep + 扩容消费者 → 积压快速下降
- **验证**：积压恢复为 0

### 场景 10：慢 SQL 打满 CPU

- **模拟**：`SELECT * FROM orders WHERE number LIKE '%xxx%'` 并发 500 次
- **现象**：CPU 100%，接口 RT 飙升
- **处理**：慢查询定位（slow_query_log）→ EXPLAIN 分析 → 加索引 / 改 SQL
- **验证**：优化后 CPU 降到 10% 以下

| **S**ituation | 项目背景、业务场景   | "在我们秒杀项目中..."                      |

### 高频场景题准备

结合这个项目，面试官可能问的场景题：

**场景 1："如果 Redis 挂了，你的秒杀还能用吗？"**

- 答：Redis 挂了后，秒杀的 Lua 脚本无法执行。降级方案是：①本地 Caffeine 缓存兜底部分读请求；②秒杀接口限流返回"活动火爆"；③DB 层用乐观锁兜底。Redis 恢复后自动重连。终极方案是 Redis Sentinel/Cluster 高可用。

**场景 2："用户下单 30 分钟后没支付，怎么取消订单？"**

- 答：通过 RabbitMQ TTL + DLX 实现。下单时发延迟消息（30 分钟），到期后消费死信：检查订单支付状态 → 未支付则取消订单 + 回补库存。为什么不直接用 Thread.sleep/Timer？因为应用重启会丢失，MQ 消息持久化更可靠。旧 15 分钟队列需在 B11 停写、排空并重建，不能原地改 TTL。

**场景 3："库存扣减怎么防止超卖？"**

- 答：三层防护。第一层：Redis Lua 脚本原子扣减（`DECRBY` + 检查负数）。第二层：DB UPDATE 语句 `WHERE stock > 0` 行级锁。第三层：数据库订单唯一索引防止重复。三层中任一层都能兜住。

**场景 4："这个项目还有什么可以改进的？"**

- 答：①加本地缓存 Caffeine 防 Redis 雪崩；②读写分离，读库减负；③分库分表，订单表按用户 ID 分片；④引入 Sentinel 做限流和熔断；⑤容器化部署，K8s 自动扩缩容；⑥加全链路压测，建立容量水位线。
