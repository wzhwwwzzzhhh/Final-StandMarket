# 第五阶段：分布式与安全实战（3步）

## Step 5.1 分布式锁全解析

### 考点覆盖

**Redis 分布式锁演进：**
- `SETNX key value` → `SET key value NX EX 30` → **Redisson** → **RedLock**
- 三大核心：**互斥**（只有一个线程持有）、**防死锁**（设置超时自动释放）、**防误删**（value 设唯一标识）

**Redisson WatchDog 原理：**
- 获取锁后启动一个定时任务（`netty` 的 `Timeout`），每 10s 执行一次
- 如果锁还在持有（业务未结束），续期 30s
- 如果业务已经完成释放锁，取消定时任务
- 问题：**GC STW > 30s 可能导致 WatchDog 无法续期，锁提前释放**

**RedLock 争议：**
- 作者 Antirez：向多数 Redis 节点（奇数台）申请锁，过半成功才算获取
- Martin Kleppmann：RedLock 不可靠，GC pause 可能导致锁失效
- 实际生产中：大多数场景单 Redis + WatchDog 已经足够

**ZooKeeper 分布式锁：**
- 临时顺序节点：创建节点成功 = 获取锁，监听前一个节点释放
- 优势：不存在锁超时问题（session 断开则自动删除）
- 劣势：性能不如 Redis（ZK 是 CP，写入性能有限）

### 项目现状

- `SeckillCouponServiceImpl:157-158` — Redisson 锁防止重复秒杀
- `RedissonConfig:28-32` — 单机模式，**没有配置超时**，使用默认值
- WatchDog 默认每 10s 续期一次，如果 GC STW 超过 10s 可能导致锁提前释放

### 模拟问题

**复现步骤：**
1. 在 `seckillCoupon()` 方法中加 `Thread.sleep(35000)` 模拟业务耗时
2. 观察 Redisson 锁：默认 WatchDog 每 10s 续期，锁应该正常
3. 模拟 FullGC STW：在业务代码中分配大对象触发 GC
4. 极端情况下锁提前释放 → 其他线程获取锁 → 同一用户可重复秒杀

### 解决方案

**1. 设置合理的 WatchDog 超时：**

```java
// WatchDog 超时 30s（默认），每 10s 续期一次
RLock lock = redissonClient.getLock("seckill:lock:" + userId);
lock.lock(30, TimeUnit.SECONDS);  // 看门狗模式，指定超时
```

**2. 加二次校验：**

```java
// 获取锁并操作 Redis Lua 后，在 Lua 脚本中已经做了
// ZSCORE 判断用户是否已购买
// 所以即使锁提前释放，Lua 脚本也会挡住重复购买
// 这是双重保障
```

**3. Lua 脚本的原子性作为最后防线（项目已具备）**

### 面试话术

> **"项目用 Redisson 分布式锁防止一人一单，WatchDog 会每 10s 续期锁。极端场景下 FullGC STW 超过 WatchDog 续期间隔可能导致锁提前释放。不过项目有双重保障——即使 Redisson 锁提前释放，Redis Lua 脚本中 `ZSCORE` 会二次判断用户是否已经购买，原子执行保证不会重复下单。面试官问 RedLock 时我还知道它的争议点：Martin Kleppmann 认为它不安全，但实际生产中用单 Redis + WatchDog 已足够。"**

## Step 5.2 分布式 ID 生成

### 考点覆盖

**雪花算法（Snowflake）结构：**

```
0 | 0000000000 0000000000 0000000000 0000000000 0 | 00000 | 00000 | 000000000000
1bit(符号位)       41bit(时间戳，毫秒级)           10bit(机器ID)  12bit(序列号)
```

- 41 位时间戳：69 年
- 10 位机器 ID：1024 台机器
- 12 位序列号：同一毫秒可生成 4096 个 ID
- 每秒可生成 409.6 万个 ID

**时钟回拨问题：**
- 机器 NTP 时间回拨 → 可能生成重复 ID
- 解决方案：
  - 记录上次时间戳，回拨时等待
  - 把机器 ID 加入 Zookeeper 序列号
  - 百度 UIDGenerator、美团 Leaf

**其他方案对比：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 本地生成，性能好 | 128 位，无序，不适合 DB 索引 |
| Redis INCR | 有序，递增 | 依赖 Redis 可用性 |
| 数据库号段（Leaf） | 趋势递增 | 依赖 DB |
| 雪花算法 | 高性能，趋势递增 | 依赖时钟 |

### 项目现状

- `UniqueID` 工具类实现雪花算法（给秒杀用）
- `OrderServiceImpl:94` — 普通订单用 `System.currentTimeMillis()`，应该替换

### 模拟问题

**复现步骤：**
1. 写测试代码 1000 并发调用 `create()` 方法
2. 收集生成的订单号，存入 Set
3. 检查是否有重复

### 解决方案

```java
// 原来
orders.setNumber("ORD" + System.currentTimeMillis());

// 改为
orders.setNumber(String.valueOf(uniqueID.nextId("order")));
```

### 面试话术

> **"订单号用 System.currentTimeMillis() 生成，1000 并发时发现重复。毫秒粒度不够并发。改用了雪花算法（项目 UniqueID 工具类）：1bit 符号位 + 41bit 时间戳 + 10bit 机器 ID + 12bit 序列号，64 位 long。同机同毫秒可生成 4096 个不重复 ID。时钟回拨问题：项目单机部署暂时安全，扩展时会考虑百度 UIDGenerator 或美团 Leaf。"**

## Step 5.3 接口防刷与安全

### 考点覆盖

**接口防刷：**
- **限流算法**：令牌桶（允许突发）、漏桶（恒定速率）、滑动窗口
- **Sentinel / Guava RateLimiter / Redisson RRateLimiter**
- **防重 Token**：每次操作前获取 token，提交时删除 token（唯一键）

**安全风险：**
- SQL 注入：MyBatis `#{}` 预编译安全，`${}` 拼接有风险
- XSS：输出编码
- 敏感配置：密钥、密码等不要硬编码

### 项目现状的安全隐患

**1. JWT 密钥硬编码：**
```yaml
# application.yml:70,76
fashion:
  jwt:
    admin-secret-key: itcast     # ❌ 默认密钥！
    user-secret-key: itheima     # ❌ 默认密钥！
```

**2. JWT 拦截器失效：**
```java
// JwtUserInterceptor:55-58
if (map.isEmpty()) {
    log.info("用户令牌不存在");
    return true;   // ❌ token 过期/无效时放行，相当于没认证！
}
```

**3. CORS 配置只允许 localhost：**
```java
// Webconfig.java
.allowedOrigins("http://localhost:3000", "http://localhost:3001", ...)
```

**4. 没有接口限流**

### 解决方案

**1. JWT 密钥改为配置占位符：**
```yaml
fashion:
  jwt:
    admin-secret-key: ${fashion.jwt.admin-secret-key}
    user-secret-key: ${fashion.jwt.user-secret-key}
```

**2. 修复拦截器：**
```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, 
                          Object handler) throws Exception {
    String token = request.getHeader("Authorization");
    if (token == null || !token.startsWith("Bearer ")) {
        response.setStatus(401);
        response.setContentType("application/json");
        response.getWriter().write("{\"code\":401,\"msg\":\"未登录或token已过期\"}");
        return false;
    }

    token = token.substring(7);
    String tokenKey = RedisKey.USER_LOGIN_KEY + token;
    Map<Object, Object> map = redisTemplate.opsForHash().entries(tokenKey);
    if (map.isEmpty()) {
        response.setStatus(401);
        response.getWriter().write("{\"code\":401,\"msg\":\"token无效或已过期\"}");
        return false;
    }
    // ...
}
```

**3. 接口限流：**

```java
// 使用 Redisson 的 RRateLimiter 限流
@Component
public class RequestRateLimiter {
    @Autowired
    private RedissonClient redissonClient;

    public boolean tryAcquire(String key, int maxPermits, int rate) {
        RRateLimiter limiter = redissonClient.getRateLimiter(key);
        limiter.trySetRate(RateType.OVERALL, maxPermits, rate, RateIntervalUnit.SECONDS);
        return limiter.tryAcquire();
    }
}

// 使用
@PostMapping("/seckill/{couponId}")
public Result seckill(@PathVariable Long couponId) {
    String ip = request.getRemoteAddr();
    if (!rateLimiter.tryAcquire("seckill:limit:" + ip, 5, 1)) {
        return Result.error("请求过于频繁");
    }
    // ...
}
```

### 面试话术

> **"安全审查发现三个问题：①JWT 密钥硬编码 'itcast'/'itheima'，攻击者可以伪造任意 token；②拦截器在 token 过期或无效时 return true 放行，认证形同虚设；③没有接口限流，攻击者可以无限刷接口。修复：密钥改从配置读取、拦截器失效返回 401、加了 Redisson RRateLimiter 限流（每 IP 每秒 5 次）。MyBatis 的 `#{}` 天然防 SQL 注入，确认了项目中所有查询都用的 `#{}`，没有 拼接的查询。"**

### 扩展思考

- Sentinel 和 Hystrix 的对比（线程隔离 vs 信号量隔离）
- 接口限流的粒度：全局限流 vs 用户级限流 vs IP 级限流
- 高并发下限流值的确定（压测得出）
