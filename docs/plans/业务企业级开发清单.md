## 清单

### 1. 秒杀链路最终一致性治理（P0）

- **背景**：秒杀链路"Redis Lua 预扣 → MQ 异步下单 → MySQL 落单"主链路已闭环，但无对账补偿。若消费者崩溃或消息丢失，Redis 已扣库存无人补回；MQ 发送在 DB 事务之外，存在"预扣成功但无单"的悬空库存。
- **核心问题**：最终一致性保障不完整。
- **候选方案**：① 本地消息表；② MQ 确认机制 + 消费重试/业务死信队列；③ 定时对账任务比对 Redis 库存 vs DB 有效订单数，悬空库存自动回补。
- **涉及模块**：`SeckillCouponServiceImpl`（MQ 投递/消费）、`DirectExchangeConfig`（重试/DLQ）、`SeckillOrderServiceImpl`、新增 `ReconciliationTask` + 对账表。
- **面试亮点**："Redis 预扣与 MySQL 落库的最终一致性如何闭环"——可靠投递、幂等消费、定时对账补偿。
- **PRD 状态**：未开始

### 2. 秒杀支付状态 bug 修复（P0，独立小项）

- **背景**：`SeckillOrderServiceImpl.confirmPayment` 先 `updateStatus(orderNumber, 2)`（置已支付）再 `updatePayTime`，而 `updatePayTime` 的 SQL 是 `status = status + 1` → 已支付(2)被加成 3(已取消)。**秒杀支付后订单变取消。**
- **核心问题**：支付状态机错误，是当前最严重 bug。
- **候选方案**：调整 `confirmPayment` 调用顺序（先 `updatePayTime` 再 `updateStatus`，或改 `updatePayTime` SQL 只写时间不改状态）；增加状态流转校验。
- **涉及模块**：`SeckillOrderServiceImpl.java:253-254`、`SeckillOrderMapper.xml`（updatePayTime）。
- **面试亮点**：状态机/乐观锁设计；能讲"我发现并修复了一个隐藏很深的并发状态 bug"。
- **PRD 状态**：未开始

### 3. 缓存一致性修复与演进（P0）

- **背景**：详情缓存已用"逻辑过期+互斥锁+异步重建"防击穿、空值缓存防穿透；但**列表缓存失效是坏的**——`ProductController.java:54/99/130` 用 `cacheClient.delete("productPage:*")`，Redis DEL 不支持通配符，管理员改商品后列表缓存**永不失效**（最长 24h 脏数据）。无随机过期防雪崩；ES 同步是全量轮询非 Canal/增量。
- **核心问题**：列表缓存失效 bug + 一致性方案不完整。
- **候选方案**：① 修 bug（scan+delete 或维护 key 索引/版本号）；② 列表缓存加空值缓存与随机过期；③ 演进为版本号/双删；④ 可选 Canal binlog 订阅同步 ES 与缓存。
- **涉及模块**：`CacheClient`（加 pattern 删除/版本号）、`UserProductController`、`AdminProductController`、`ProductIndexServiceImpl`。
- **面试亮点**：缓存穿透/击穿/雪崩/一致性的完整解决方案 + 真实踩坑（`*` 不能删），对比双删与 Canal 取舍。
- **PRD 状态**：未开始

### 4. 消息可靠性加固（P1）

- **背景**：延迟队列+死信队列已做，消费端按订单号二次查重；但消费者抛异常走**默认无限 requeue**（无最大重试、无业务毒消息 DLQ），库存扣减失败会死循环；无手动 ACK 配置、无消息轨迹。
- **核心问题**：消费异常无上限重试、毒消息无归宿。
- **候选方案**：配置最大重试 + 业务死信队列；手动 ACK；记录消息轨迹（发送/消费/失败）。
- **涉及模块**：`SeckillCouponServiceImpl` 消费端、`DirectExchangeConfig`、RabbitMQ 配置。
- **面试亮点**：消息可靠投递的完整链路；面试问"MQ 怎么保证不丢消息/不重复消费"直接有实例。
- **PRD 状态**：未开始

### 5. 可观测性建设（P1）

- **背景**：全项目无 MDC TraceId、无 Micrometer/Prometheus、无 APM、无统一日志格式，Sentinel 只有本地限流无控制台指标。
- **核心问题**：线上无法定位问题。
- **候选方案**：日志加 MDC TraceId（过滤器注入）；引入 Micrometer + Prometheus + Grafana；暴露核心指标（QPS/RT/线程池/MQ 积压）；Sentinel 接入控制台。
- **涉及模块**：新增 `TraceIdFilter`、pom 加依赖、`application.yml`、`Webconfig`。
- **面试亮点**："线上怎么定位问题"——链路追踪 + 指标大盘，简历写"生产级可观测性"。
- **PRD 状态**：未开始

### 6. 真实性能压测落地（P1）

- **背景**：JMeter 报告全部"待环境执行"，压测从未真正跑起来，无基线数据。理论瓶颈：消费者单行 `reduceStock` 行锁争用、支付 sleep 占用连接、列表缓存脏读。
- **核心问题**：性能优化没有数据支撑。
- **候选方案**：准备环境（MySQL/Redis/MQ/JMeter）真实执行已备好的 3 个压测场景；产出优化前后对比报告（QPS/RT/错误率/超卖数）。
- **涉及模块**：`jmeter/*.jmx`、`docs/plans/JMeter压测报告.md`、按结果定位瓶颈。
- **面试亮点**：真实性能数据 + "我压测到 X QPS、0 超卖"。
- **PRD 状态**：未开始

### 7. 接口幂等框架（P2）

- **背景**：秒杀靠 Redisson 锁+Lua 防重、券靠 CAS 乐观锁、支付回调靠 `status==0` 判断；但无统一幂等框架，退款申请用"先查再插"（并发可重复提交），无唯一索引兜底。
- **核心问题**：幂等散落各处，退款等场景有并发重复风险。
- **候选方案**：统一幂等注解 + 幂等表（业务键+状态），核心写接口套用；退款表加唯一索引兜底。
- **涉及模块**：新增幂等切面/注解、`RefundServiceImpl`、相关 Mapper。
- **面试亮点**：接口幂等的统一设计；面试问"怎么防重复提交/重复回调"直接有框架。
- **PRD 状态**：未开始

### 8. 代码架构优化（P2）

- **背景**：`SeckillOrderServiceImpl`(461 行) 是上帝类，混 CRUD/统计/支付模拟/算价；`listAll()` 与 `listUserOrders()` 有 N+1 循环查库；异常处理 try/catch 吞掉返回 null；`OrderServiceImpl.pay` 在事务内 `Thread.sleep(1.5~3s)` 占连接池；`AgentServiceImpl` 硬编码 `localhost:8000` 无视配置；空接口 `SeckillService` 是死代码。
- **核心问题**：可维护性与潜在性能隐患。
- **候选方案**：拆上帝类（统计/支付/算价抽离）；修 N+1（关联查询）；统一异常处理；支付 sleep 移出事务；AgentServiceImpl 读配置；删死代码。
- **涉及模块**：`SeckillOrderServiceImpl`、`OrderServiceImpl`、`AgentServiceImpl`、`SeckillService`。
- **面试亮点**：代码质量与重构；面试问"你做过哪些重构"有具体案例。
- **PRD 状态**：未开始

### 9. 分布式事务治理（P2，作为最终一致性治理的深化延伸）

- **背景**：当前靠最终一致性（MQ 异步）而非强事务；秒杀跨 Redis/MySQL 无分布式事务。
- **核心问题**：是否需要更强的一致性保障。
- **候选方案**：与事项 1 联动评估——本地消息表已足够则无需 Seata；若需强事务引入 Seata AT/TCC。
- **涉及模块**：评估后定。
- **面试亮点**：能讲清"最终一致性 vs 强事务的取舍"，何时该用 Seata。
- **PRD 状态**：未开始（依赖事项 1 结论）
