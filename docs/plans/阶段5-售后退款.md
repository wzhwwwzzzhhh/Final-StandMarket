# Phase 5: 售后/退款

> 基于主计划 [功能拓展主计划.md](功能拓展主计划.md) Phase 5
> 日期: 2026-07-19

## Context

Phase 4 已完成物流发货流程，订单状态机现在完整覆盖"待付款→待发货→已发货→已完成"。Phase 5 的目标是增加售后/退款能力：

- **用户端**：已支付订单可申请退款（发货前/后均可）
- **管理端**：审核退款申请（同意/拒绝），同意后恢复库存
- **状态机扩展**：增加 `status=6（退款）`

### 当前订单状态机

```
1(待付款) → 支付 → 2(待发货) → 发货 → 3(已发货) → 确认收货 → 4(已完成)
                                                     取消 → 5(已取消)
                                                    申请退款 → 6(退款)
```

### 退款业务流程

```
用户申请退款
  → 系统创建 refund 记录（status=0 待审核）
  → 管理端查看退款申请列表
  → 管理员审核：
    ├ 同意退款 → 更新 refund.status=2 + 恢复库存 + 订单 status=6
    └ 拒绝退款 → 更新 refund.status=3 + 填写审核意见
```

### 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 退款范围 | 整单退款（非部分退款） | MVP 简化，`order_detail_id` 字段保留为后续扩展 |
| 退款触发 | 仅已发货(3)/已完成(4)订单可申请 | 待付款/待发货走取消流程，无需退款 |
| 库存恢复 | 同意退款时恢复（product 级别） | order_detail 无 sku_id，MVP 先恢复 product 表库存，后续可细化到 SKU |
| 退款金额 | 订单实付金额 | 无部分退款，按订单 `amount` 全额退款 |
| 退款单号 | `RF` + 时间戳 | 区别于订单号 `ORD` 前缀 |
| 退款前状态保存 | refund 表加 `order_status` 字段 | 拒绝退款时恢复订单到此状态 |

## 步骤

### Step 1: 数据库 — 创建 refund 表

```sql
CREATE TABLE `refund` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键',
  `order_id` bigint NOT NULL COMMENT '订单id',
  `order_detail_id` bigint DEFAULT NULL COMMENT '订单详情id（部分退款，预留）',
  `user_id` bigint NOT NULL COMMENT '用户id',
  `refund_no` varchar(50) NOT NULL COMMENT '退款单号',
  `reason` varchar(500) DEFAULT NULL COMMENT '退款原因',
  `amount` decimal(10,2) NOT NULL COMMENT '退款金额',
  `status` tinyint NOT NULL DEFAULT '0' COMMENT '状态 0待审核 2已退款 3拒绝',
  `order_status` tinyint DEFAULT NULL COMMENT '申请退款时的订单状态（拒绝时恢复用）',
  `audit_opinion` varchar(500) DEFAULT NULL COMMENT '审核意见',
  `audit_time` datetime DEFAULT NULL COMMENT '审核时间',
  `refund_time` datetime DEFAULT NULL COMMENT '退款完成时间',
  `create_time` datetime NOT NULL COMMENT '创建时间',
  `update_time` datetime DEFAULT NULL COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `idx_refund_no` (`refund_no`),
  KEY `idx_refund_order` (`order_id`),
  KEY `idx_refund_user` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb3 COLLATE=utf8mb3_bin COMMENT='退款/售后';
```

SQL 脚本保存至 `mysql/refund_table.sql`。

### Step 4: 后端 — RefundService

**新增文件**：`backend/fashion-server/src/main/java/com/fashion/service/RefundService.java`

接口方法：
```java
/**
 * 申请退款
 */
Refund apply(Long orderId, String reason);

/**
 * 获取用户的退款记录
 */
List<Refund> listUserRefunds();

/**
 * 管理端获取所有退款记录
 */
List<Refund> listAllRefunds(Integer status);

/**
 * 同意退款（恢复库存 + 更新订单状态）
 */
void approve(Long id, String opinion);

/**
 * 拒绝退款
 */
void reject(Long id, String opinion);
```

**新增文件**：`backend/fashion-server/src/main/java/com/fashion/service/impl/RefundServiceImpl.java`

关键实现逻辑：

1. **`apply()`**：
   - 校验订单存在性 + 当前用户归属
   - 校验订单状态（status === 3 或 4，仅已发货/已完成可退）
   - 校验是否已存在该订单的退款申请（status < 2 的）
   - 生成退款单号 `RF` + 时间戳
   - 插入 refund 记录，同时保存当前订单状态到 `order_status` 字段（拒绝时恢复用）
   - 更新订单 status = 6（退款中）

2. **`approve()`**：
   - `@Transactional`
   - 校验 refund 状态为 0（待审核）
   - 更新 refund.status = 2（已退款），设置 refundTime、auditOpinion、auditTime
   - 遍历订单商品详情，恢复库存（product 表 `stock` 或 `sales` 字段）
   - 订单 status 保持 6（退款状态）

3. **`reject()`**：
   - 校验 refund 状态为 0
   - 更新 refund.status = 3（拒绝），设置 auditOpinion、auditTime
   - 用 refund.order_status 恢复订单状态（apply 时保存的原值）

### Step 5: 后端 — 库存恢复逻辑

`order_detail` 表没有直接关联 `product_sku.id`，仅有 `product_id` 和 `sku_info`（字符串）。MVP 阶段按 **product 级别**恢复库存，后续可细化到 SKU 级别。

**新增文件**：`backend/fashion-server/src/main/java/com/fashion/mapper/ProductSkuMapper.java`

```java
public interface ProductSkuMapper {
    @Update("UPDATE product_sku SET stock = stock + #{delta} WHERE product_id = #{productId}")
    int restoreStockByProductId(@Param("productId") Long productId, @Param("delta") Integer delta);
}
```

在 `RefundServiceImpl.approve()` 中：
- 查询 `order_detail` 获取该订单所有商品及数量
- 对每个商品调用 `productSkuMapper.restoreStockByProductId(productId, number)`
- `@Transactional` 保证原子性

## 验证方式

1. **后端编译**：`mvn clean compile -DskipTests` 成功
2. **数据库验证**：`SHOW CREATE TABLE refund` 确认表结构
3. **退款申请测试**：
   - 已支付订单 → 点击"申请退款" → 填写原因 → 提交成功
   - 数据库中 refund 表新增记录 status=0
   - 订单 status 变为 6
4. **审核测试**：
   - 管理端退款列表显示待审核记录
   - 点击"同意退款" → 库存恢复 → refund status=2
   - 点击"拒绝退款" → 填写意见 → refund status=3
5. **边界情况测试**：
   - 未支付订单点击退款 → 提示不可退款
   - 同一订单重复申请退款 → 提示已有退款处理中
   - 管理端同意退款后库存正确恢复
